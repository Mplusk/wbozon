# Оценка спроса

Модуль считает баллы по пяти признакам раздела 6.1 ТЗ: объём (вес 25), доступность (20), вход новичков (20), цена (20), устойчивость (15). Начальный порог 60 из 100. Это сумма **обоснованных оценок аналитика**: значения `score_fraction` от 0 до 1 умножаются на соответствующий вес. ТЗ не определяет, как превращать объём, долю лидеров или тренд в баллы; этот переход код не придумывает, оценка и объяснение задаются явно. Значение 0 — реальная оценка, отсутствие оценки блокирует результат.

Все пять факторов и диапазон цен требуют источника и даты, а факторы — пояснения оценки. Ссылки и другие сведения об источниках — утверждения вызывающего кода: модуль не подтверждает их достоверность, достаточность, актуальность и право на использование. В обосновании следует указать период и числовые данные — например 30 дней для объёма и 12 месяцев для тренда. Код не добывает рыночные данные и не устанавливает спрос самостоятельно; нужен отдельный источник.

Вход передаётся по stdin команде `python3 -m demand`. JSON имеет форму:

```json
{
  "assessment": {
    "factors": {
      "volume": {"score_fraction": 0.5, "source": "условный отчёт", "observed_at": "2026-11-12", "rationale": "пример: оценка 0.5"},
      "accessibility": {"score_fraction": 0.5, "source": "условный отчёт", "observed_at": "2026-11-12", "rationale": "пример"},
      "newcomers": {"score_fraction": 0.5, "source": "условный отчёт", "observed_at": "2026-11-12", "rationale": "пример"},
      "price": {"score_fraction": 0.5, "source": "условный отчёт", "observed_at": "2026-11-12", "rationale": "пример"},
      "stability": {"score_fraction": 0.5, "source": "условный отчёт", "observed_at": "2026-11-12", "rationale": "пример"}
    },
    "price_range": {"min_rub": 700, "max_rub": 1200, "source": "условный обзор", "observed_at": "2026-11-12"}
  }
}
```

Числа в примере условные, не данные Ozon. Удобно сохранить вход в JSON и вызвать `python3 -m demand < input.json`. Опциональные поля верхнего уровня `weights` и `threshold` позволяют передать решения о весах и пороге; веса должны быть неотрицательны и суммарно давать 100. Перед изменением параметров требуется соответствующее решение владельца. Неполный вход возвращает `status: blocked` с перечислением проблем и код процесса 2, без итогового балла. Результат `assessed` не является одобрением товара и не заменяет проверку экономики или ревизора. Числа JSON выводятся строками там, где используется точная десятичная арифметика.

## Сохранение оценки для кандидата

Для уже созданного кандидата на стадии `demand` команда `python3 -m demand.record_cli --db /защищённый/путь/store.sqlite3 < assessment.json` берёт последнюю версию из локальной базы, рассчитывает оценку и сохраняет новую версию с полями `demand.score`, `price_min`, `price_max`, `source`, а также всеми факторами, обоснованиями, датами, весами и порогом. Переход стадии и внешние действия не выполняются. История предыдущих версий сохраняется; SQLite-база не является неизменяемым журналом или защищённой авторизацией.

Вход для этой команды содержит `candidate_id`, `assessment` (объект из примера выше), `source` (ссылка или обозначение общего пакета подтверждающих материалов) и `observed_at` (ISO-дата и время с часовым поясом, например `2026-11-12T12:00:00Z`). Опционально можно передать `weights` и `threshold`. Каждому фактору и диапазону по-прежнему нужны собственные источник, дата и обоснование. Источники не верифицируются автоматически. Не указывайте секреты и персональные данные в источниках или файлах.

Неполные данные, отсутствующий кандидат или другая стадия дают `blocked` и не создают новую версию. Завершённая оценка сохраняется и когда балл ниже порога, но это не разрешает переход. Функция `pipeline.blockers` по умолчанию использует порог 60; если владелец явно изменил порог, вызывающий код должен передать такой же `demand_threshold` в проверку перехода.
