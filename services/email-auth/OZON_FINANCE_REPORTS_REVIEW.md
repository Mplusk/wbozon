# Независимая проверка финансовых инструментов Ozon

Дата проверки: 17 ноября 2026 года. Проверены локальные изменения рабочей копии
относительно `6f06dacf1a3d07a44086d353cfe2c7ca74567e22`. Проверяющий использовал
только синтетические входы, подставной транспорт и локальный WSGI MCP; реальные
учётные данные, кабинет и API Ozon им не использовались. Код реализации не
изменялся. Хеши ниже относятся к проверенной рабочей копии.

## Заключение

На проверенных синтетических сценариях блокирующих дефектов частичного
локального контракта не обнаружено. Это не приёмка полной финансовой сводки:
полнота начислений за период, идентичность и аддитивность строк, историческая
принадлежность SKU, распределение общих расходов, фактические покупательские
выкупы и совпадение с кабинетом независимо не подтверждены. Сопоставление
реальных данных и приёмка полного отчёта остаются **blocked**.

## Сообщение исполнителя о staging

По сообщению исполнителя, при ограниченной проверке staging на реальном Ozon
прошли проекции дневных начислений в режимах `summary` и `details`, а также
прямое и обратное сопоставление через `ozon_product_info`. Затем запрос
`/v1/finance/accrual/postings` получил HTTP 429, после чего проверочный
скрипт остановился. Значение заголовка `Retry-After` скрипт не сохранил, поэтому
срок ожидания неизвестен; это не утверждение, что Ozon не прислал заголовок.
Исполнитель сообщил, что дальнейшие финансовые запросы приостановлены до
проверки срока восстановления.

Эти сведения приведены со слов исполнителя: независимый ревизор не подключался
к staging и не видел ответы Ozon. Результат отдельных чтений не подтверждает
полноту периода, точность финансового итога, работу всех сценариев, публикацию
исправлений или приёмку полного отчёта.

`ozon_accrual_day` возвращает одну страницу на дату начисления и выбранные
наблюдаемые SKU. В `summary` арифметика известных строк разделена по SKU,
компоненту, типу и валюте. `financial_total` остаётся `null`, включая пустую
страницу. Счётчики и `coverage_by_sku` показывают отсутствующие суммы, валюты и
контейнеры; полнота каждой группы остаётся непроверенной. `known_amounts`
считает только значения с известными и суммой, и валютой. Поля, исключённые из
сводки, перечислены в `not_in_summary`; для них доступен `details`, кроме
`commission_ratio`, которое не возвращается и оговорено в результате. Повторный
вызов `details` не гарантирует тот же снимок данных.

Повторяющиеся проекции не удаляются как доказанные дубли; уникальность строк и
финансовая аддитивность не подтверждены. Два поля комиссии представлены разными
компонентами. Их нельзя автоматически складывать друг с другом, с ценами или с
итогами доставки; итог доставки может включать отдельные услуги. Начисления без
привязки к SKU не распределяются по товарам. Пустой курсор сам по себе не
доказывает полноту дня; клиент должен отслеживать курсоры и ID между страницами.

Категории типов назначены локально по ограниченным точным парам названия и
описания; `other` означает «не классифицировано», а не подтверждённую прочую
статью. Независимая проверка не сверяла эти пары с ответом реального кабинета
и не подтверждала полноту классификации. Знак начисления сохраняется по
данным Ozon; категория возврата не означает количество возвращённых товаров.

`ozon_realization_article_month` отбирает строки месячного отчёта по точному
артикулу. Арифметика количеств относится к наблюдённым строкам, не доказанному
итогу выкупов. При отсутствии соответствующих структур сумма `null`, а не
подтверждённый ноль; знак возврата сохраняется. Месяц отчёта не является
недельным фильтром по дате заказа, а последующие возвраты не подтверждены.
`ozon_orders_analytics` отдельно помечает отсутствие дат и непроверенную
полноту периода; пустой ответ не преобразуется в подтверждённые нули.

По [объявлению Ozon от 24 августа 2026 года](https://dev.ozon.ru/news/783-Izmeneniia-v-metodakh-dlia-raboty-s-finansovymi-otchetami-v-Seller-API/),
новые финансовые запросы следует выполнять последовательно и данные могут
отличаться от кабинета. [Описание новых методов Ozon](https://dev.ozon.ru/community/2008-Novye-beta-metody-dlia-polucheniia-nachislenii/)
различает начисления по отправлениям, справочник типов и начисления за день.
Читаемую схему и однозначное условие окончания страниц `by-day` эта независимая
проверка не получила. [Разъяснение Ozon о фактических выкупах](https://dev.ozon.ru/community/1809-API-metod-dlia-fakticheskikh-vykupov/)
ссылается на месячные отчёты реализации; оно не подтверждает доступность и
полноту выкупов за произвольную неделю конкретного продавца.

Новые финансовые методы включены в существующий gate. На синтетике 429
сохраняет cooldown, который блокирует последующий финансовый вызов того же
Client ID. Gate действует только для процессов с одним общим доверенным
каталогом; другие интеграции, тома и хосты он не координирует. Неизвестный
исход не повторяется автоматически. Кратковременно предложенный fallback к
`STATE_DIRECTORY`, способный сменить namespace сохранённого gate, удалён;
фактический путь и состояние gate на сервере в этой проверке не исследовались.

Ответ Ozon ограничен 512 000 байтами до локального фильтра SKU или артикула;
большой месячный отчёт или страница может не загрузиться даже в `summary`.
Отдельно ограничен размер ответа MCP; в проверенных сценариях при превышении
возвращается ошибка вместо усечения. Независимый ревизор не проверял внешний
сервер, опубликованный MCP, Claude, Linux, сборку контейнера и GitHub Actions.
`test_release` не запускался
из-за зависимости от Linux-модуля `fcntl`; Dockerfile и `.dockerignore`
проверены статически.

## Проверки

Рабочая папка: `services/email-auth`. Ниже `$python` — исполняемый Python из
локального Codex runtime. Для всех вызовов использовались фиктивные ответы и
ключи. Прямой расширенный прогон до последнего уточнения полей summary:

```powershell
$python = Join-Path $env:USERPROFILE '.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe'
& $python -B -m unittest -q test_ozon_finance_reports test_ozon_posting_candidates test_ozon_article_summary test_ozon_posting_status test_finance_gate test_ozon_details test_ozon_mcp test_external_mcp test_external_mcp_integration test_ozon_response_guard test_provider_payload.ProviderPayloadTests test_provider_deadline
```

Результат: **156 тестов, OK**. После последней правки явных исключений
`summary` и верхнего `financial_total` выполнен повтор затронутых тестов:

```powershell
& $python -B -m unittest -q test_ozon_finance_reports test_external_mcp test_external_mcp_integration
```

Результат: **41 тест, OK**. Набор включает синтетические вызовы обоих новых
инструментов через авторизованный MCP, проверку общего cooldown, отказ при
дублированных ключах JSON и при превышении входного лимита.

После финальной правки выполнены ещё **6 независимых синтетических проб, OK**:
точность `0.1 + 0.2 − 0.3`, разделение валют и отсутствие суммы; 2200 значений
с 50 целыми и 20 дробными разрядами при входе меньше лимита; отсутствие валюты;
пропущенные контейнеры по SKU; сохранение повторных строк и разделение полей
комиссии; перечисление исключённых из summary полей и `null` при пустой
странице. Эти разовые пробы запускались через Python stdin и не сохранены как
отдельный файл. Ранее также независимо проверены два локальных WSGI MCP вызова
и блокировка второго инструмента после фиктивного 429 первого.

Во время ревизии исполнителю переданы и им исправлены: ложные нули при отсутствии
месячных данных, непривязанный к прежнему состоянию fallback финансового gate,
неполная проверка формата дат отчёта, безусловная полнота аналитики заказов,
скрытые пропуски и исключённые поля компактной сводки, а также неподходящие
подсказки при превышении размера. Явно отмечены непроверенная аддитивность и
неполная классификация. `git diff --check` завершился успешно с предупреждениями
о переводах строк; неотслеживаемые файлы он не проверяет.
