# Независимая проверка Ozon finance gate

Дата: 17 ноября 2026 года. Область проверки — локальные изменения финансовых инструментов, шлюза и их интеграции. Использовались фиктивные данные, тестовые каталоги и транспорт без сети. Реальный API, сервер, ключи, развёртывание, Linux и GitHub Actions не проверялись.

## Финансовые данные

Публичное [объявление Ozon](https://dev.ozon.ru/community/2008-Novye-beta-metody-dlia-polucheniia-nachislenii/) определяет `postings` как начисления по выбранным отправлениям, а `by-day` — за день. Более поздняя [новость Ozon](https://dev.ozon.ru/news/783-Izmeneniia-v-metodakh-dlia-raboty-s-finansovymi-otchetami-v-Seller-API/) допускает расхождения с кабинетом. Правила уникальности одинаковых строк, их финансовой аддитивности и окончательной полноты в доступных первичных материалах независимо не подтверждены; страница полной схемы Seller API текстовому инструменту не раскрылась.

На фиктивных данных две одинаковые проекции в одном отправлении и одна в другом сохранены как три строки. Совпадение отмечено внутри первого отправления, `observed_row_sum` является арифметикой наблюдаемых строк, а `financial_total` остаётся `null`. Период фильтруется по дате начисления. Отсутствующие отправления и строки без SKU не распределяются автоматически. Совпадение проекций не доказывает ни дубль, ни самостоятельную операцию.

Полная сводка по артикулу, фактические выкупы, прибыль и выплата на единицу **не подтверждены и не реализованы**. Совокупность всех отправлений и расходов за период этот инструмент не получает.

## Шлюз и проверки

Команда, выполненная из `services/email-auth`:

```text
python -B -m unittest -q test_finance_gate test_ozon_details test_external_mcp test_ozon_mcp test_external_mcp_integration test_ozon_response_guard test_provider_deadline
```

Результат: **104 теста прошли** на Windows. Дополнительно выполнены **10 независимых синтетических сценариев** и отдельные проверки настоящего `Portal` с фиктивным gateway и opener. Среди них:

- MCP и `/api/read` с одним Client ID и общим каталогом: пока один вызов исполняется, второй получает `busy` и не попадает в gateway; после завершения вызов разрешается.
- Потеря пары файлов клиента, замена каталога и откат только внутреннего состояния блокируют запрос; завершение отдельного тестового процесса через `os._exit` оставляет неопределённый исход. Неизвестный `Retry-After` и смена boot identity со скачком системных часов не снимают ожидание автоматически.
- HTTP-date без заголовка `Date` не превращается в нулевой интервал. Совпадение фиктивного ключа с интервалом не раскрывается в MCP или `/api/read` и сохраняет неопределённое ожидание.
- При известном HTTP 200 слишком большое тело даёт `provider_response_too_large`, после чего следующий синтетический запрос может выполняться. Невалидное тело и timeout чтения после заголовков также не оставляют ложную неопределённость; timeout до заголовков её оставляет. Ошибка локальной TLS-подготовки до обращения к провайдеру не блокирует следующий запрос.
- Для 5000 фиктивных строк ответ провайдера укладывался во входной лимит, но подробная MCP-проекция превышала выходной: вместо усечения возвращён `response_too_large`; summary сохранил число всех 5000 строк.

Ранее обнаруженные обходы потери файлов, ложного финансового `total`, отражения числового интервала и блокировки после известного успешного HTTP-ответа были исправлены исполнителем и повторно проверены в указанных границах. `git diff --check` не нашёл ошибок пробелов; Git предупредил о преобразовании переводов строк. Тест `test_release` на Windows отдельно не импортировался из-за отсутствия `fcntl` и не засчитан как прошедший. Docker-сборка не выполнялась.

## Ограничения

- Координация работает только между процессами, использующими один и тот же корректно настроенный общий каталог, локальные файловые блокировки и устойчивое хранилище. Другие приложения, каталоги, тома и серверы с тем же Client ID не контролируются; фактические настройки эксплуатации не проверялись.
- Для неизвестного срока или исхода финансовые чтения намеренно остаются заблокированными. Локальная процедура из `PORTAL.md` требует независимой проверки времени сброса; сама функция доказательство не проверяет. Автоматического восстановления нет.
- Проверен воспроизводимый предел anti-rollback: откат только внутреннего каталога обнаруживается, но согласованный откат внутреннего состояния и соответствующего внешнего epoch того же клиента не обнаруживается, даже если прочие marker и registry остались нетронутыми. Старый согласованный снимок нельзя считать актуальным без внешнего доверенного источника.
- Безопасность замены каталога во время активного запроса на Linux не проверена. В синтетической попытке на Windows ОС отказала в перемещении открытого каталога; результат не является доказательством поведения Linux. Нельзя менять или восстанавливать файлы gate во время работы без отдельной процедуры.
- Для отдельного большого отправления входной лимит провайдера может быть непреодолим: `view=summary` уменьшает только выход MCP, не исходный ответ Ozon. Права ключа, стабильность API и полный набор необходимых данных не проверены.
