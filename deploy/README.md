# Подготовка CD для VPS

Это **неустановленный шаблон**, а не действующее развёртывание. VPS самостоятельно забирает `main` по SSH, запускает обязательные модули и все найденные `unittest`, затем атомарно переключает ссылку `current` на каталог проверенного релиза. При ошибке клонирования или тестов активная ссылка не меняется; при повторном обнаружении того же коммита новый релиз не создаётся. Старые релизы сохраняются: для них ещё нужна политика очистки. Скрипт не отправляет и не изменяет данные в маркетплейсах.

Это пока **выкладка файлов**, а не готовое обновление работающих сервисов: ни systemd-сервисы приложения, ни их перезапуск, smoke-тест или автоматический откат после неудачного перезапуска не реализованы. Локальные тесты не доказывают, что сервис заработает. Запуск по таймеру не означает, что появились автономные агенты. Каталоги создаются с правами 0700; прежде чем отдельный пользователь сервиса сможет читать релиз, администратору понадобится отдельно и безопасно настроить доступ на чтение, не открывая ключи и изменяемые данные. Сценарий валидации реализует GitHub SSH repository `git@github.com:OWNER/REPOSITORY.git` или `ssh://git@github.com/OWNER/REPOSITORY.git`; необходим защищённый `main` и действующий read-only deploy key.

## До настройки

1. По ТЗ сменить ранее раскрытый root-пароль, защитить SSH и инвентаризировать VPS. Настройку выполняет администратор, с учётом уже работающих на сервере систем.
2. Создать отдельного непривилегированного пользователя для выкладки, **отдельного от пользователей сервисов**. Его не следует допускать к пользовательским данным, базе, ключам маркетплейсов и Telegram. Разместить изменяемую конфигурацию, данные и резервные копии вне релизов и вне доступа этого пользователя; при дальнейшей интеграции приложения обеспечить отдельную передачу нужной конфигурации сервису.
3. Настроить для пользователя выкладки SSH-ключ с правом только чтения выбранного приватного GitHub-репозитория. Ключ хранится только на VPS, в защищённом каталоге пользователя; `known_hosts` подготовить, сверив отпечаток публичного ключа сервера GitHub с официальным источником. Подключения используют `StrictHostKeyChecking=yes`, запросы пароля и SSH-agent forwarding не включаются.
4. На VPS должны быть Git, Python 3 и systemd. Каталог `/srv/wbandozon` принадлежит пользователю выкладки, не доступен на запись другим пользователям и не содержит чужих данных. Путь должен быть на одной файловой системе для атомарного переключения.

**Граница безопасности:** тесты выполняют код из `main` от имени пользователя выкладки. Они могут получить доступ к файлам и read-only SSH-ключу, доступным этому пользователю, и изменить его файлы. Фильтрация переменных окружения не является песочницей. Поэтому защищайте `main` и изолируйте deploy-пользователя от бизнес-секретов и сервисных данных. Никаких ключей и токенов в репозиторий или в командную строку.

## Установка администратором

В инструкциях ниже пути даны как пример; не выполнять их, пока не проверены VPS, пользователь и права.

1. Скопировать проверенный `deploy/deploy.py` в `/opt/wbandozon-deployer/deploy.py` и обеспечить его защиту от изменений пользователем выкладки. Это отдельный доверенный управляющий файл: содержимое `deploy.py` из релиза **не обновляет** его автоматически; управляющий файл обновляют отдельно после проверки.
2. Изменить в копии `wbandozon-deploy.service` URL и пути на ваши. Unit предназначен для systemd **пользовательской службы** deploy-пользователя; он не должен запускаться от root. `WorkingDirectory`, `ExecStart`, `ReadWritePaths` и каталог базы должны существовать и соответствовать правам пользователя.
3. Установить копии `wbandozon-deploy.service` и `wbandozon-deploy.timer` в пользовательский каталог systemd, перезагрузить конфигурацию `systemctl --user daemon-reload` и сначала выполнить `systemctl --user start wbandozon-deploy.service`. По `journalctl --user -u wbandozon-deploy.service` проверить результат и `current`.
4. Только после успешной проверки включить таймер `systemctl --user enable --now wbandozon-deploy.timer`. Для работы без интерактивного входа может потребоваться настройка пользовательского systemd администратором. Отключение: `systemctl --user disable --now wbandozon-deploy.timer`.

Не подключайте к `current` сервисы, пока не реализованы безопасное обновление, рестарт, проверка состояния и откат. Любой реальный доступ и работа на VPS требуют отдельной проверки. `python3 -m unittest -v test_deploy` проверяет сценарии локально на временном репозитории и не обращается к серверу или GitHub.
