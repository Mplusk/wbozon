# Action Gateway: безопасный прототип без записи в Ozon

FastAPI-приложение предоставляет журнал и постоянную аварийную остановку. **Любая заявка на изменение кабинета отвергается**: ни один внешний write-адаптер пока не реализован и режима включения записи нет. Режим только чтения включён по умолчанию, остановка сохраняется в SQLite после перезапуска. База и журнал — прототип на SQLite, не защищённый от изменений пользователя файловой системы и не заменяющий резервное копирование.

На сервере задать для процесса через защищённый менеджер секретов/конфигурацию окружения:

- `GATEWAY_DB_PATH` — абсолютный путь к базе в защищённом каталоге; каталог должен существовать.
- `GATEWAY_OWNER_TOKEN`, `GATEWAY_AGENT_TOKEN` — два разных случайных токена длиной не менее 32 печатных ASCII-символов без пробелов. Владелец имеет право остановки и чтения журнала; агент — только чтения состояния и подачи заявок. Не передавать их в аргументах, URL, журнале, Git или чате.

После установки совместимых зависимостей и задания среды запускается локально:

```bash
python3 -m uvicorn gateway.app:create_from_env --factory --host 127.0.0.1 --port 8000
```

Для внешнего доступа необходимы отдельно настроенные HTTPS, защита секретов, изоляция сервисного пользователя, ограничение доступа к БД и обратный прокси с ограничением размера запроса; эти настройки здесь не создаются. Токены должны передаваться через `Authorization: Bearer …`, а не в ссылках. Состояние и журнал — `GET /v1/status` и только для владельца `GET /v1/audit`; журнал выводит события, время и хеши идентификаторов без тел и токенов. `POST /v1/actions` принимает только фиксированные типы действий и заголовок `Idempotency-Key` длиной 8–128 символов из `[A-Za-z0-9_.:-]`. Повтор того же запроса возвращает сохранённый результат, а повтор ключа с другим содержимым даёт конфликт. Пока все такие запросы отвергаются.

`POST /v1/stop` доступен только владельцу, требует `Idempotency-Key`, переводит базу в остановку и проверяет отказ отдельной пробной заявки. Успешное подтверждение возвращается, только если оба признака `stopped` и `probe_denied` истинны. Возобновление записи отсутствует. Для Telegram-бота доступен локальный `GatewayStore(absolute_db_path).stop_and_probe(request_id)`: бот обязан самостоятельно удостоверить владельца до вызова и использовать **ту же базу**. Серверная функция не удостоверяет Telegram ID. После сбоя между остановкой и проверкой остановка сохраняется, подтверждать её следует лишь после успешного повторного probe.

`gateway/policy.py` содержит изолированные расчётные проверки цены, рекламных бюджетов, оценки отзыва, лимитов печати и условий публикации; неизвестные данные блокируются. **Они ещё не подключены к HTTP-маршрутам как разрешение действий**: для этого нужны защищённые и актуальные серверные данные, подтверждения владельца, независимая ревизия и атомарное связывание решения с операцией и журналом. Цифры, присланные агентом, не считаются доверенным состоянием. Реальную запись в Ozon нельзя включать до реализации и тестирования этих механизмов, адаптеров, сверки неопределённого результата и аварийного режима.

Тесты без сети: `python3 -m unittest -v test_gateway test_gateway_policy`.

## Координация остановки с локальными процессами

На одном VPS доверенные процессы используют одну и ту же базу шлюза и `GatewayStore(path).coordination_lock()`. Под этой блокировкой они повторно проверяют `status()['stopped']` и выполняют только локальные изменения, которые должны сериализоваться с остановкой. Вызов `stop_and_probe` сам берёт тот же межпроцессный lock; вложенный захват запрещён. Сетевые запросы под lock запрещены; остановка не отменяет сетевой запрос Telegram или будущего внешнего адаптера, уже отправленный до её фиксации. При тайм-ауте или ошибке блокировки следует прекратить работу, не подтверждая операцию. Сам режим остановки отличается от `read_only`: последний включён и до остановки.

Lock использует `flock` и файл в каталоге базы. База не может быть символической ссылкой или иметь жёсткие ссылки, каталог должен принадлежать сервисному пользователю и быть защищён от посторонней записи. Все процессы должны работать от того же доверенного пользователя с единым каноническим путём. Механизм не защищает от прямых изменений SQLite, обхода функции или подмены файлов со стороны пользователя с такими правами; подключать недоверенные процессы к базе нельзя. Он предполагает корректный `flock` локальной файловой системы и не является распределённой блокировкой для нескольких серверов.
