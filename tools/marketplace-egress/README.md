# Ограниченный маршрут к API маркетплейсов

Схема: портал на portal host → SSH local forward на `127.0.0.1:18761` → loopback-прокси на relay host → фиксированные API. Прокси разрешает HTTP CONNECT на порт 443 для фиксированных доменов Ozon, Wildberries и Авито, включая `api.avito.ru`. Полный список задаёт константа `ALLOWED` в `marketplace_proxy.py`. Остальные имена, адреса, порты и методы отклоняются до DNS. После DNS исключаются непубличные и multicast-адреса, и соединение открывается по проверенному адресу. Клиент обязан проверять TLS-сертификат и имя исходного API; прокси не расшифровывает TLS и не хранит/логирует токены, HTTP-заголовки или содержимое.

Прокси слушает только IPv4 loopback relay host. До 8 одновременных подключений; заголовки до 8 КиБ и 5 секунд, DNS до 3 секунд, подключение до 5 секунд, простой туннеля до 20 секунд, полная жизнь туннеля до 60 секунд и общий объём до 8 МиБ. Превышение лимитов и ошибки разрывают соединение. Это не глобальное ограничение частоты запросов. Локальные процессы relay host и portal host также могут обратиться к соответствующему loopback-порту; по портам отдельно не устанавливается идентичность локального пользователя. Изоляция от других локальных пользователей при необходимости требует дополнительных мер ОС.

## До установки

Проверить на обоих серверах ОС, свободность `127.0.0.1:18761`, совместимость unit-файлов, открытый исходящий SSH с portal host и DNS/TLS к двум API с relay host. Проверить ограничения systemd, текущие пользователи и работающие сервисы. Выпуск и установку интегрировать с принятой процедурой отката; не перезаписывать существующие файлы/пользователей без проверки. Сохранить вне журналов и репозитория приватный ключ для отдельного туннеля. До добавления `known_hosts` независимо сверить SSH host key relay host по доверенному каналу. Портал должен использовать только проверку TLS обычного системного доверия или заранее проверенные настройки CA.

## Подготовка relay host

1. Создать отдельного непривилегированного системного пользователя `marketplace-egress` без доступа к данным и секретам портала. Защитить `/opt/marketplace-egress` и скрипт от записи этим пользователем; установить `marketplace_proxy.py` и unit `marketplace-egress-proxy.service`. Скрипт слушает только 127.0.0.1, настройка bind отсутствует намеренно. Выполнить `systemd-analyze verify` и проверить запуск в нужном sandbox, прежде чем включать unit.
2. Создать отдельного SSH-пользователя `relay-account` без доступа к бизнес-данным. Его домашний каталог и `.ssh/authorized_keys` должны быть защищены от записи этим пользователем. Убедиться, что политика учётной записи позволяет только public-key вход; отсутствие пароля не должно блокировать использование ключа. Не использовать root-ключ.
3. В `authorized_keys` разрешить **только** специально созданный открытый ключ с опциями `restrict,port-forwarding,permitopen="127.0.0.1:18761",command="/bin/false"` перед ключом. На уровне `Match User relay-account` дополнительно обеспечить `AuthenticationMethods publickey`, `PasswordAuthentication no`, `KbdInteractiveAuthentication no`, `AllowTcpForwarding local`, `AllowStreamLocalForwarding no`, `PermitOpen 127.0.0.1:18761`, `PermitTTY no`, `AllowAgentForwarding no`, `X11Forwarding no`, `PermitTunnel no`, `GatewayPorts no`, `ForceCommand /bin/false`. Проверить поддержку директив текущим sshd и влияние действующих Match-блоков; сначала `sshd -t` и `sshd -T -C ...`, а изменение sshd выполнять так, чтобы не потерять текущую админ-сессию. SSH `-N` не открывает shell/session и допускает только указанный локальный forward. Проверить отдельным подключением, что shell, PTY, другой адрес/порт, remote forwarding и streamlocal forwarding запрещены. Подробности с путями учётных записей должны определяться по фактической конфигурации сервера.

## Подготовка portal host

1. Создать отдельного непривилегированного пользователя `marketplace-tunnel`. Разместить ключ в `/etc/marketplace-egress/tunnel-key` с владельцем `marketplace-tunnel`, правами 0600 и защищённым от записи каталогом. В `/etc/marketplace-egress/known_hosts` указать независимо проверенный host key relay host; файл должен быть защищён от записи пользователем сервиса.
2. Установить unit `marketplace-egress-tunnel.service`, проверить его `systemd-analyze verify`. Он выполняет `ssh -N -T` с закреплённым host key и строго локальным `-L`; сервис переподключается при обрыве. Проверить, что `127.0.0.1:18761` появился только на loopback, а попытки использовать иной адрес/порт через SSH запрещены.
3. Лишь после проверки отдельно настроить `HTTPS_PROXY` и `https_proxy` для процесса портала на `http://127.0.0.1:18761`. Сверить существующие `NO_PROXY`/`no_proxy`: совпадение имён API обойдёт прокси; не удалять другие нужные исключения без проверки. Любой другой HTTPS-клиент портала унаследует те же настройки и будет ограничен перечисленными хостами; проверить совместимость остальных операций. Поставщик TLS проверяет исходные имена, а не адрес прокси. Изменения unit/drop-in, перезапуск и откат выполнять только согласно проверенному эксплуатационному порядку приложения.

На текущем сервере портала в том же systemd drop-in задано `GUNICORN_CMD_ARGS=--timeout 60`: это оставляет запас относительно 20-секундного ограничения сетевого подпроцесса и ожидания базы при высокой нагрузке. При переносе или обновлении unit необходимо сохранить обе настройки и проверить фактическую конфигурацию Gunicorn. Таймаут воркера не является гарантией максимальной длительности всего пользовательского запроса.

## Проверка без ключей маркетплейсов

`python3 -m unittest -v` в этом каталоге запускает тесты с синтетическими данными, без сети к API. После настройки SSH-туннеля на portal host можно проверить два разрешённых домена запросом `curl --noproxy '' --proxy http://127.0.0.1:18761 --connect-timeout 6 --max-time 12 --output /dev/null --silent --show-error --write-out '%{http_code}\n' https://api-seller.ozon.ru/` и аналогично `https://discounts-prices-api.wildberries.ru/`. Ответ HTTP (включая отказ без ключа) подтверждает прохождение TLS и доступность адреса, но не действительность ключа, права кабинета или исправление конкретного запроса. Для запрещённого домена запрос через прокси должен быть отклонён. Затем отдельно оценить работу портала и существующих сервисов. Не включать подробные curl/SSH/HTTP-логи и не выводить конфигурацию, содержащую секреты.

Отключение: остановить только оба новых unit и убрать только специально добавленный drop-in портала согласно процедуре отката. Не менять другие прокси, SSH-настройки, приложения и данные. Имена и пути выше — шаблон, не свидетельство установленной инфраструктуры.
