# Бот решений владельца

Это серверный long-polling адаптер Telegram Bot API. Токен бота и идентификаторы пользователя/чата задаются только серверному сервису через защищённое окружение. Модуль не принимает webhook и не выдаёт агентам доступ к ключам или прямым действиям в маркетплейсах. Реальный аккаунт и VPS не проверялись.

Официальная документация Telegram Bot API: [getUpdates](https://core.telegram.org/bots/api#getupdates), [CallbackQuery](https://core.telegram.org/bots/api#callbackquery), [sendMessage](https://core.telegram.org/bots/api#sendmessage), [answerCallbackQuery](https://core.telegram.org/bots/api#answercallbackquery), [InlineKeyboardButton](https://core.telegram.org/bots/api#inlinekeyboardbutton). getUpdates не работает одновременно с активным webhook; проверить настройку бота оператору до запуска.

## Настройка на сервере

Приложение требует отдельного непривилегированного пользователя, TLS, доступ к `api.telegram.org`, закрытый каталог данных и корректно настроенный часовой пояс. Настроить перечисленные переменные **в защищённом окружении этого сервиса**, без вставки значений в чат, Git, командную строку, unit-файлы или системный журнал:

- `TELEGRAM_BOT_TOKEN` — токен бота, созданного владельцем.
- `TELEGRAM_OWNER_USER_ID` и `TELEGRAM_OWNER_CHAT_ID` — два проверенных владельцем числовых ID для его приватного чата с ботом. Оба обязательны: ни группы, ни каналы не допускаются.
- `TELEGRAM_GATE_DB` — абсолютный путь к существующей базе кандидатов и решений владельца.
- `TELEGRAM_GATEWAY_DB` — абсолютный путь к отдельной базе состояния шлюза.
- `TELEGRAM_CURSOR_DB` — абсолютный путь к отдельной базе курсора и состояния доставки бота. Базы не должны совпадать; каталог должен быть доступен только нужному пользователю. Новые файлы создаются с правами 0600.

Серверные хранилища доступны только этому боту и уполномоченным сервисам, не исполнителям-агентам. Не раздавать права прямой записи в базы агентам: проверки пользователя в Python не защищают их от подмены базы или исполнения кода на сервере.

После отдельной настройки окружения и реестра кандидатов запустить:

```bash
python3 -m bot poll --once   # одна проверка, включая доставку ожидающих запросов
python3 -m bot poll          # непрерывный процесс
```

После обработки входящих обновлений приложение проверяет остановку шлюза, затем `gates.worker.scan` создаёт необходимые заявки на текущей стадии и выбирает ожидающие через `GateStore.list_pending`. Актуальность проверяется через `describe`; владелец видит **весь** пакет решения, вид операции, идентификатор, версию и срок. При активном стопе или недоступности статуса новые заявки не создаются и не рассылаются. При ошибке подготовки заявок обработка последующих `/stop` сохраняется. Если пакет не помещается в Telegram, он не отправляется. Кнопка содержит только случайный идентификатор из сервера и выбор; подлинность решения определяется по ответу Telegram, sender ID, ID приватного чата и проверкам реестра.

`python3 -m bot send --nonce <идентификатор>` принудительно отправляет уже существующую активную заявку; это действие также проходит через журнал доставки. Состояние можно проверить администратору: `python3 -m bot delivery-status --nonce <идентификатор>`. Не помещайте настоящие значения nonce в публичные логи или обсуждения. Проверка/запросы должны поступать из серверных сервисов, а не быть общедоступным API для агентов.

Доставка сначала получает статус `started`, затем `sent`. Состояния `unknown` и `started` означают, что Telegram мог получить сообщение при потере ответа или сбое процесса; `blocked` означает, что пакет не был отправлен из-за проверки. **Автоматического повтора нет**: владелец или оператор сначала сверяет чат и состояние заявки и, если требуется, создаёт новый запрос в реестре после истечения или отмены предыдущего. Не удаляйте записи журнала доставки вслепую. Отправка callback-ответа после сохранения решения не является доказательством получения сообщения владельцем.

При подтверждении sample, launch или publication бот вызывает `transition_decided`: стадия меняется только после проверок серверного реестра. Если процесс упал между записью решения и переходом, повтор того же обновления завершит переход идемпотентно. Отдельное подтверждение rights фиксирует права и само стадию не меняет. Ошибка условий или устаревшая ревизия не запускает переход; права и остальные критические данные привязаны к точной версии.

`/stop` принимается только от заданного владельца в заданном приватном чате. При обработке пакета обновлений стоп выполняется в первую очередь, чтобы ошибка предыдущего callback не заблокировала аварийную остановку. При активном стопе callback отклоняется и об этом сообщается владельцу; при недоступном статусе шлюза решение не обрабатывается и смещение обновлений не продвигается. После команды шлюз фиксирует read-only режим и выполняет проверочную попытку записи; подтверждение отправляется только если оба результата истинны. Повтор обновления безопасен. После остановки автоматическое включение записи не реализовано.

Смещение getUpdates хранится локально после записи эффекта. При сбое до фиксации смещения обновление может быть получено снова; реестр решений защищён от повтора по update_id. Источники, факт ревизии, целостность SQLite и реальное поведение внешних сервисов здесь не удостоверяются. Операционные журналы должны содержать только фиксированные ошибки, не URLs Telegram с токеном или содержимое сообщений.

Тестирование без секретов и сети: `python3 -m unittest -v test_telegram_bot`. Проверки содержат имитации Bot API и локальные SQLite базы; они не заменяют пробный запуск с владельцем.

## Неустановленный systemd-шаблон

`systemd/wbandozon-telegram.service` — шаблон пользовательской службы для выделенного непривилегированного аккаунта бота. Он не установлен и не запущен. Перед его применением администратор должен проверить VPS, создать три закрытых каталога данных, сделать релиз доступным пользователю бота только на чтение, настроить виртуальное окружение Python и заменить `WorkingDirectory`, `ExecStart`, `EnvironmentFile` и `ReadWritePaths` на реальные пути. Запись должна быть разрешена только в каталоги конкретных БД. Файл среды в примере `/var/lib/wbandozon/secrets/telegram.env` должен находиться вне Git, принадлежать пользователю бота и иметь права 0600; доступ к нему и конфигурации systemd ограничивается на уровне ОС. В файл записываются только серверные значения перечисленных переменных, а не параметры командной строки.

Из сессии выделенного пользователя после проверки прав администратор устанавливает unit в его каталог systemd, запускает `systemctl --user daemon-reload` и `systemctl --user start wbandozon-telegram.service`; при успешной проверке может включить автозапуск через `systemctl --user enable wbandozon-telegram.service`. Для работы без активной пользовательской сессии может потребоваться настройка systemd администратором. Шаблон не регистрирует webhook, не разворачивает проект и не изменяет маркетплейсы.

Состояние шлюза и решения ворот хранятся в разных базах SQLite. Для согласованных серверных процессов `/stop`, решения и восстановление worker сериализуются общей межпроцессной блокировкой рядом с базой шлюза; сетевые вызовы не удерживают блокировку. Все процессы обязаны использовать один канонический путь к этой базе, одного доверенного пользователя ОС и эту реализацию: прямое изменение SQLite или копии обходят механизм. Начатую отправку Telegram стоп не отзывает; новые ответы после стопа не принимаются. До production необходима настройка прав и испытания реальной связки; этот прототип не является тампероустойчивым журналом.
