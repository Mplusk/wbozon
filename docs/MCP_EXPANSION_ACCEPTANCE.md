# Расширение MCP для Ozon и Wildberries

Спецификация и сверка публичных контрактов от 18 ноября 2026 года. В каталоге 46 инструментов, включая 24 из этого расширения. Все проходят через авторизацию кабинета и шлюз чтения. Разрешённые методы и пути заданы в `market_transport.py`. Создание задачи отчёта инициирует выгрузку у площадки. Методам управления поставками, рекламой, ценами и остатками доступ закрыт.

## Как прочитать результат

У ответа есть `items`, время наблюдения UTC, `complete` и `next_cursor`. Для следующей страницы передайте `next_cursor` в указанный у инструмента параметр `cursor`, `page` или `offset`. При `status=pending` повторите те же параметры после `retry_after_seconds`. Для асинхронного отчёта можно также передать его `task_id`. Итог финансовой сводки за период появляется после подтверждённого окончания обхода. `null` означает отсутствие известного значения. В `summary_scope` различаются итоги страницы и всего периода.

Даты без времени обозначают отчётный день соответствующего источника. Для статистики WB это московский календарь. Суммы группируются по валюте источника. В аналитике Ozon валюта компании приводится отдельно от валюты суммы. В складских строках WB `sku_basis=wb_barcode` обозначает штрихкод варианта. Для точной связи площадок передайте `mapping` или задайте псевдоним в приватном файле `supply-articles.json` рядом с БД кабинета. Например, значение `{"пример":{"ozon_offer_id":"TEST-OZ","wb_vendor_code":"TEST-WB","wb_nm_id":71}}` сопоставляет два разных тестовых артикула. Имя товара само по себе не определяет соответствие.

Секреты Ozon Performance вводятся отдельно в кабинете и хранятся в зашифрованном хранилище. Для запроса по артикулу рекламный отчёт связывается с каталогом на стороне сервера. Для выгрузки по известному SKU достаточно рекламных учётных данных. Ключ WB должен иметь категорию нужного метода. Для обогащения строк артикулами нужен также доступ к каталогу.

## Девять вопросов приёмки

Каждая строка реализована и проверяется на фикстурах в указанном объёме. Колонка реальной приёмки относится к данным продавца через опубликованный MCP. В этом выпуске она остаётся открытой для всех девяти вопросов.

| № | Что можно воспроизвести через MCP | Проверка на фикстурах | Реальный источник и условие |
| --- | --- | --- | --- |
| 1 | Перечислить поставки за полгода, пройти составы, сопоставить заявленное и принятое | `test_supply_goods_retains_real_receipt_and_box_contents`, `test_supply_items_keep_requested_and_received_distinct_by_act`; проверены курсоры и несовпавшие акты | Нужны права FBW/FBO и опубликованные акты. Полугодовой реестр продавца не проверялся. |
| 2 | Остаток и транзит по складам, дни покрытия | `test_raw_marketplaces_use_exact_mapped_articles_and_distinguish_transit` | Покупательский транзит не используется как новая поставка. Для проверки нужны реальные складские отчёты. |
| 3 | Темп заказов за 7/30/90 дней по складам и кластерам | `test_exact_windows_include_zero_days_and_ceiling_before_subtracting_units`, `test_missing_warehouse_cluster_cannot_look_like_a_complete_cluster_plan` | Охват FBO и FBW. Неизвестное соответствие склада кластеру показано в результате. |

## Проверка версии

Идентификатор проверенного дерева Git для `services/email-auth` — `314466bd9ab24416cdcda739b8903ba62125c903`. Его можно сверить командой `git rev-parse HEAD:services/email-auth`. По итогам двух независимых проверок прошли 114 тестов пяти профильных модулей с синтетическими данными, включая конфликты курсоров, выплат, заказов и статусов приёмки. SHA-256 архивного примера Ozon Performance — `980e0bc42aa75c3e59e151ce62f49394485dd648989ba151cd184d1b988cc96f`.

Код расширения зафиксирован 18 ноября 2026 года в `6a151a6`. В Ubuntu прошли 586 тестов сервиса и изолированная проверка Docker. Автопроверка содержимого архива сверяет все 98 файлов сервиса с Git. Журнал доставки приведён отдельно от проверки приложения. [Коммит расширения](https://github.com/Mplusk/wbozon/commit/6a151a6bc4313b0eed3ac15058206651c13a4cb0) · [Запуск GitHub Actions](https://github.com/Mplusk/wbozon/actions/runs/44251587995) · [Проверка приложения](https://github.com/Mplusk/wbozon/actions/runs/44251587957)

Третья попытка этого запуска получила подтверждение контрольной суммы от staging. SHA-256 доставленного архива — `a3fd45c18b4c919b0eab956b056500838ea2e7943c568724f797a63b2fff7057`. На том же дереве сервиса две версии официального Python SDK, 1.26.0 и 2.3.0, независимо подключились по Streamable HTTP к локальному WSGI-серверу с тестовым Bearer-ключом. Каждый клиент получил 46 инструментов и выполнил 24 вызова `tools/call` с ответами площадок из `test_expansion_mcp`. Для этого прогона сеть ограничивалась loopback. [Подтверждение staging](https://github.com/Mplusk/wbozon/actions/runs/44251587995/job/134635781527) · [Официальный Python SDK](https://github.com/modelcontextprotocol/python-sdk)

В корне репозитория идентификатор проверяемой версии даёт `git rev-parse HEAD`. В каталоге `services/email-auth` проверку расширения воспроизводит команда:

```sh
python3 -B -m unittest -v test_expansion_mcp test_wb_expansion_contracts test_ozon_expansion_contracts test_market_ads_contracts test_supply_plan_contracts
```

Независимые проверки адаптеров используют синтетические ответы. Проверка приложения проходит реальную авторизацию и `tools/list` / `tools/call` через WSGI, включая изолированный subprocess для запроса без сетевого источника. В Linux CI дополнительно запускаются полный набор тестов, сетево изолированный Docker smoke, тесты системного контроллера и тестирование содержимого упакованного кандидата. Для этой ветки `native-stage` доставляет архив в закрытое хранилище кандидатов. Контроллер рабочего сервиса сохраняет свою политику разрешённых версий.

Статистика WB кэшируется на 30 минут. Известный ID формируемого отчёта сохраняется до проверки состояния. После неопределённого результата создания сервер останавливает автоматические новые запросы на создание до сверки с площадкой. Защищённые контрольные точки разделены по учётным данным. История склада хранит последнее наблюдение UTC за день для успешно прочитанных полных наборов складов. Она пополняется при чтении, ограничена 365 днями и объёмом приватного хранилища. Время, когда товар получил нулевой остаток между двумя наблюдениями, из этих данных установить нельзя.

При ротации ключа для его новых запросов создаётся отдельная область снимков и контрольных точек. В `marketplace_total` общий баланс при свободном перемещении запасов отделён от суммы поставок по направлениям без переброски между кластерами Ozon или складами WB. Поля `ship_without_transfers_without_inbound` и `ship_without_transfers_if_inbound_arrives` дают эти два сценария. При неполных данных по направлениям значения остаются пустыми.
