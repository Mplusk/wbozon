# Расширение MCP для Ozon и Wildberries

Спецификация и сверка публичных контрактов от 18 ноября 2026 года. В каталоге 46 инструментов, включая 24 из этого расширения. Все проходят через авторизацию кабинета и шлюз чтения. Разрешённые методы и пути заданы в `market_transport.py`. Создание задачи отчёта инициирует выгрузку у площадки. Методам управления поставками, рекламой, ценами и остатками доступ закрыт.

## Как прочитать результат

У ответа есть `items`, время наблюдения UTC, `complete` и `next_cursor`. Для следующей страницы передайте `next_cursor` в указанный у инструмента параметр `cursor`, `page` или `offset`. При `status=pending` повторите те же параметры после `retry_after_seconds`. Для асинхронного отчёта можно также передать его `task_id`. Итог финансовой сводки за период появляется после подтверждённого окончания обхода. `null` означает отсутствие известного значения. В `summary_scope` различаются итоги страницы и всего периода.

Даты без времени обозначают отчётный день соответствующего источника. Для статистики WB это московский календарь. Суммы группируются по валюте источника. В аналитике Ozon валюта компании приводится отдельно от валюты суммы. В складских строках WB `sku_basis=wb_barcode` обозначает штрихкод варианта. Для точной связи площадок передайте `mapping` или задайте псевдоним в приватном файле `supply-articles.json` рядом с БД кабинета. Например, значение `{"пример":{"ozon_offer_id":"TEST-OZ","wb_vendor_code":"TEST-WB","wb_nm_id":71}}` сопоставляет два разных тестовых артикула. Имя товара само по себе не определяет соответствие.

Секреты Ozon Performance вводятся отдельно в кабинете и хранятся в зашифрованном хранилище. Для запроса по артикулу рекламный отчёт связывается с каталогом на стороне сервера. Для выгрузки по известному SKU достаточно рекламных учётных данных. Ключ WB должен иметь категорию нужного метода. Для обогащения строк артикулами нужен также доступ к каталогу.

## Проверка на данных продавца

**Состояние на 18 ноября 2026 года.** Для исходной ревизии `d02d578` в GitHub проверены запуск CI, список окружений, список развёртываний и переменных Actions. Окружений, записей о развёртывании и переменных с адресом отдельного MCP не обнаружено. Задание доставки подтвердило архив SHA-256 `2ee25c52da2729572c42669c6210215dd29c1f3bd346f8427d08681bf751745d`. Приёмник сохраняет его в приватный каталог. Задание активации рабочего сервиса пропущено. Отдельное запущенное приложение с разрешённым доступом к кабинетам не установлено по доступным сведениям. Во всех девяти строках статус проверки на реальных данных — **blocked**. [Запуск CI](https://github.com/Mplusk/wbozon/actions/runs/44259199627) · [Приёмник архива на проверенной ревизии](https://github.com/Mplusk/wbozon/blob/d02d5782f4b621dccd8f561725445f98eb14a817/tools/native-release/stage_receiver.py)

Для снятия общего блокера нужен изолированный работающий экземпляр проверенной сборки, адрес его Streamable HTTP MCP и отдельно разрешённое подключение продавца только на чтение. Оператор стенда сверяет SHA запущенной сборки и контрольную сумму с манифестом CI. Клиент согласует протокол своим SDK (`initialize` и `notifications/initialized` либо `server/discover` для поддерживающих его версий), выполняет `tools/list` и сохраняет версию протокола, `serverInfo` и имена инструментов. Строка версии протокола и количество инструментов сами по себе SHA сборки не идентифицируют.

В примерах ниже каждая строка JSON — параметры запроса MCP `tools/call`. `TEST-OZ`, `TEST-WB`, 71, номера поставок, складов и кампаний — **тестовые подстановки**. В ходе приёмки они заменяются точными идентификаторами из ответов этого же кабинета. Для Ozon начать с `ozon_product_info({"offer_ids":["TEST-OZ"]})` и сохранить все SKU и схемы. Для WB пройти карточки `wb_products({"limit":100})` с парой возвращённых курсоров до точного совпадения артикула и nmID. Несколько несовместимых соответствий блокируют проверку конкретного товара.

Сначала выполнить короткую проверку P0 по одному складу, одной поставке или одному дню. Продолжать последовательно в пределах действующих методных лимитов. На 429 или `pending` сохранить параметры, идентификатор задачи и курсор, продолжить после `Retry-After` или `retry_after_seconds`. При неизвестном сроке разблокировки дождаться подтверждения площадки. На 403 зафиксировать площадку и недоступную категорию. Повтор страницы с тем же курсором, противоречие идентификаторов или отсутствующее значение пометить как неполноту. Для каждой проверки сохранить приватно SHA, инструмент, период и часовой пояс, время наблюдения, число страниц и уникальных строк, итог сравнения и пропуски. Ключи доступа и полные ответы продавца в отчёт не включаются.

### 1. Поставки и приёмка за полгода

```jsonl
{"name":"wb_supplies","arguments":{"date_from":"2026-05-18","date_to":"2026-11-17","limit":10,"mode":"details"}}
{"name":"wb_supply_goods","arguments":{"supply_id":19,"article":"TEST-WB","nm_id":71,"mode":"details"}}
{"name":"ozon_supply_orders","arguments":{"date_from":"2026-05-18","date_to":"2026-11-17","limit":20,"mode":"details"}}
{"name":"ozon_supply_items","arguments":{"order_id":42,"supply_id":77,"bundle_id":"TEST-BUNDLE","article":"TEST-OZ","mode":"details"}}
```

Для WB период ограничивает дату создания по Москве, для Ozon — начало таймслота UTC. Это разные основания выборки. Пройти списки и составы до конца по `offset` на WB и `cursor` на Ozon. Для предзаказа WB использовать `preorder_id` с `is_preorder=true`. Сверить артикул, nmID или SKU и позиции каждой поставки. На WB отдельно сложить заявленное и принятое, сверить полный состав с деталями поставки. Короба служат контрольной сверкой. На Ozon одни и те же акты могут повторяться на страницах состава. Дедуплицировать по поставке и идентификатору акта, сопоставить строки по SKU и типу. Сохранить фактическое и согласованное количество. Пока акты на согласовании или расходятся, окончательный приём остаётся открытым. Сейчас отсутствуют реальный реестр и связанные акты обеих площадок.

### 2. Остатки, транзит и дни покрытия

```jsonl
{"name":"wb_stocks","arguments":{"article":"TEST-WB","nm_id":71,"mode":"details"}}
{"name":"ozon_stocks_by_cluster","arguments":{"article":"TEST-OZ","mode":"details"}}
{"name":"ozon_stocks","arguments":{"article":"TEST-OZ","mode":"details"}}
```

Отчёт WB продолжать по тому же `task_id`, страницы выгрузки — по `offset`. Сложить складские строки по вариантам и сверить с отдельным итогом WB. Транзит к покупателю и от него вывести отдельно. На Ozon сверить все релевантные SKU, склад и кластер, доступный запас и транзит в поставках. Строки FBS сверять в отчёте по схемам. Показатели `present`, резерва и доступного FBO-запаса имеют разные определения. Сопоставить дни покрытия с расчётом № 5 на наблюдениях того же времени. Сейчас отсутствуют два реальных складских отчёта и время их наблюдения.

### 3. Заказанные единицы по направлениям за 7, 30 и 90 дней

```jsonl
{"name":"wb_orders","arguments":{"article":"TEST-WB","nm_id":71,"date_from":"2026-08-20","date_to":"2026-11-17","limit":100,"mode":"details"}}
{"name":"ozon_fbo_postings_geo","arguments":{"article":"TEST-OZ","date_from":"2026-08-20","date_to":"2026-11-17","limit":100,"mode":"details"}}
```

Пройти `cursor` по исходным страницам, включая отфильтрованные пустые страницы с продолжением. На дату проверки 18 ноября окна завершаются 17 ноября и начинаются 11 ноября, 19 октября и 20 августа. ## Приёмка через изолированный MCP

Клиент `tools/mcp_acceptance.py` запускается из checkout рабочей ветки. Один запуск создаёт один новый JSON-файл. Без `--scenario` он проверяет ответ 401 с Bearer challenge, отпечаток исходников работающего сервиса, согласование протокола и полный каталог инструментов. При несовпадении отпечатка в первом ответе клиент останавливается до отправки ключа. Каждый используемый инструмент должен объявлять доступ только на чтение. Сценарий делает вызовы только после этих проверок.

Для проверки на данных продавца нужен отдельный экземпляр проверенной сборки со своими БД, хранилищем ключей и каталогом лимитов. Его хранилище должно быть подключено к разрешённым кабинетам через штатный шлюз чтения. Стендовый MCP-ключ поступает в окружение **клиента** под именем `SIDZEN_ACCEPTANCE_TOKEN` из защищённого хранилища. Проверка использует уже выданные права. В сценарии 8 для Ozon дополнительно нужны учётные данные Performance этого стенда. Доставка архива CI в staging сама по себе создаёт только файл-кандидат. Для ревизии сервиса `96dc3b2` доставка прошла, шаг production пропущен. [Журнал сборки](https://github.com/Mplusk/wbozon/actions/runs/44267440982)

На уже подготовленном стенде фабрика из `tools/mcp_acceptance.py` оборачивает штатный портал и добавляет к ответу `/mcp` заголовок `X-Sidzen-Service-SHA256`. В окружении **сервиса** должны быть заданы `SIDZEN_ACCEPTANCE_ROOT`, `BASE_URL=https://127.0.0.1:8765`, а также пути существующих `DATABASE_PATH`, `VAULT_PATH` и `OZON_FINANCE_GATE_DIR` внутри этого каталога. Файлы `SESSION_SECRET_FILE`, `VAULT_KEY_FILE`, `READ_TOKEN_HASH_FILE` и опциональный `MCP_READ_TOKEN_HASH_FILE` берутся из отдельного каталога стенда или его `CREDENTIALS_DIRECTORY`. Для следующей команды нужны checkout с клиентом, распакованный и проверенный по манифесту CI архив сервиса, интерпретатор его окружения и собственный TLS-сертификат стенда с IP `127.0.0.1` в SAN.

```sh
"$WBOZON_STAGE_PYTHON" -m gunicorn --chdir "$WBOZON_STAGE_RELEASE/service" \
  --pythonpath "$WBOZON_CHECKOUT/tools" --bind 127.0.0.1:8765 --workers 1 \
  --certfile "$WBOZON_STAGE_CERT" --keyfile "$WBOZON_STAGE_KEY" \
  'mcp_acceptance:create_stage_app()'
```

На стенде с уже запущенной фабрикой достаточно следующей команды из checkout. При частном центре сертификации `SSL_CERT_FILE` в окружении клиента указывает на его доверенный CA. Клиент использует адрес `https://127.0.0.1:8765/mcp` по умолчанию. Другой порт или IPv6 loopback можно передать через `--endpoint`. Редиректы и системные прокси отключены. Укажите полный Git SHA ожидаемой сборки. Клиент запишет его и сравнит отпечаток исполняемых Python-модулей портала с тем же деревом в Git. Отпечаток архива с зависимостями проверяется отдельно по манифесту CI.

```sh
python3 tools/mcp_acceptance.py --expected-commit bed0c74cdbc320ceaf3763f596c260ae998f5530 --output evidence/preflight-01.json
```

Для каждого из девяти вопросов укажите его номер отдельным запуском. Например, для плана поставки на 21 день и для октябрьской выплаты команды выглядят так.

```sh
python3 tools/mcp_acceptance.py --scenario 5 --expected-commit bed0c74cdbc320ceaf3763f596c260ae998f5530 --output evidence/05-plan-01.json
python3 tools/mcp_acceptance.py --scenario 7 --month 2026-10 --expected-commit bed0c74cdbc320ceaf3763f596c260ae998f5530 --output evidence/07-payout-01.json
```

Для товарных вопросов клиент находит Ozon `300030` и WB `3000030` в каталогах соответствующих площадок. Он использует все найденные SKU Ozon. Если заранее известны обязательные SKU, каждый можно передать через `--expect-ozon-sku`. В сценарии 4 укажите нужные склады отдельными `--warehouse-id`. В сценарии 8 можно ограничить выбор повторяемыми `--wb-campaign-id` и `--ozon-campaign-id`, иначе клиент проверяет кампании из доступного списка. Для сценариев 6–9 по умолчанию выбран октябрь 2026 года. В сценарии 9 сравнивается предшествующий месяц. Для календарного среза P0 есть `--as-of YYYY-MM-DD`; история заказов заканчивается накануне, по календарю WB или Ozon. Прошлую дату текущего складского остатка и прошлые слоты этим параметром восстановить нельзя.

Код выхода 0 и `preflight_ok` подтверждают доступ к каталогу. `evidence_ready` означает, что проверки выбранного вопроса выполнены и доказательства готовы для независимой приёмки. Код 2 и один из статусов `partial`, `blocked`, `pending` сохраняют причину. Среди них неполная пагинация, несовместимый SKU, истёкшая задача, недоступная категория, отсутствие исторических снимков и ограничение периода. Охват прав отражает фактически вызванные методы. В JSON остаются период, версия, число страниц и наблюдений, результаты сверок и доступная задержка повтора. Содержимое строк продавца, суммы, номера поставок, кампаний, задач, курсоры и ключи в файл не записываются.

Создание задач отчётов допускается при явном выборе требующего их сценария. По умолчанию клиент завершает запуск при ожидании отчёта или 429. Чтобы дождаться указанной площадкой задержки в том же запуске, задайте, например, `--max-wait 120`. Внутри одного запуска клиент сохраняет известный ID задачи в памяти и следует курсорам. При исчерпании бюджета или неизвестной задержке сохраняется текущий статус. Следующий запуск использует другое имя файла и повторно сверяет страницы, опираясь на штатные контрольные точки шлюза. Отдельные частичные результаты не складываются.

Для локального воспроизведения без кабинетов выполните `python3 -m unittest -q test_mcp_acceptance test_mcp_acceptance_scenarios`. Фикстуры покрывают положительные и неполные данные для всех девяти вопросов, обрыв пагинации, истёкшую задачу, неподходящую версию, отсутствие SKU и прав, а также 429 и повтор с сохранением задачи.

В Linux CI дополнительно запускаются полный набор тестов, сетево изолированный Docker smoke, тесты системного контроллера и тестирование содержимого упакованного кандидата. Для этой ветки `native-stage` доставляет архив в закрытое хранилище кандидатов. Контроллер рабочего сервиса сохраняет свою политику разрешённых версий.

Статистика WB кэшируется на 30 минут. Известный ID формируемого отчёта сохраняется до проверки состояния. После неопределённого результата создания сервер останавливает автоматические новые запросы на создание до сверки с площадкой. Защищённые контрольные точки разделены по учётным данным. История склада хранит последнее наблюдение UTC за день для успешно прочитанных полных наборов складов. Она пополняется при чтении, ограничена 365 днями и объёмом приватного хранилища. Время, когда товар получил нулевой остаток между двумя наблюдениями, из этих данных установить нельзя.

При ротации ключа для его новых запросов создаётся отдельная область снимков и контрольных точек. В `marketplace_total` общий баланс при свободном перемещении запасов отделён от суммы поставок по направлениям без переброски между кластерами Ozon или складами WB. Поля `ship_without_transfers_without_inbound` и `ship_without_transfers_if_inbound_arrives` дают эти два сценария. При неполных данных по направлениям значения остаются пустыми.
