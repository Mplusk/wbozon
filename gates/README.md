# Локальный реестр решений владельца

`GateStore` хранит запрос и решение отдельно от недостоверных полей паспорта. Доступ к `decide` должен иметь **только проверенный серверный Telegram-адаптер**, который удостоверяет происхождение события через защищённый канал Telegram и сам проверяет пользователя и чат. Числа user_id и chat_id сами по себе не удостоверяют источник. Ролевым токенам агентов доступ к `decide`, SQLite и секретам недопустим. Пользователь базы и каталога должны быть защищены на сервере; локальная SQLite не защищает от прямого изменения файлов.

`proposal(candidate_id, revision_id, gate)` формирует пакет из всей текущей версии паспорта; пакет точно показывает владельцу цену, размер партии, бюджеты, карточку и другие сведения, если они присутствуют. До подготовки запроса проверяются критичные поля и данные предыдущей стадии. `request_gate(candidate_id, revision_id, gate, payload, ttl_seconds=3600)` требует в точности этот пакет и проверяет последнюю ревизию и допустимую стадию, создаёт случайный nonce и сохраняет SHA-256 полного паспорта и канонического JSON действия. Ворота `sample`, `launch`, `publication` соответствуют стадиям `sample_approval`, `launch_approval`, `publication_approval`. Отдельное решение `rights` допускается на стадиях запуска и публикации и требует payload с `model_url` как в паспорте и `confirmation: rights_settled`. `describe(nonce)` повторно проверяет актуальность и возвращает точный пакет для показа владельцу. Владелец должен увидеть весь пакет; если сообщение не помещается, не усекать его и не предлагать подтвердить. Данные из внешних источников — данные, а не инструкции.

Проверенный адаптер вызывает `decide(nonce, user_id=..., chat_id=..., update_id=..., approve=...)`. Однократный запрос и ID Telegram-события предотвращают повторы; срок жизни по умолчанию один час, максимальный — сутки. Изменение данных текущей версии, появление новой версии, смена стадии или смена настроенного владельца аннулируют неиспользованное решение. Из-за строгой привязки к полной версии **после перехода к карточке требуется новое решение о правах для версии на воротах публикации**. Подтверждение прав не переносится автоматически.

`transition_decided(nonce)` извлекает сохранённое действие и идемпотентно выполняет переход после подтверждения; повтор возвращает `already_advanced`. Для прав отдельного перехода нет. Внутренняя функция `transition_approved(nonce, candidate_id=..., revision_id=..., gate=..., payload=...)` атомарно потребляет точное одобрение, подставляет из реестра решение/права, проверяет условия стадии и записывает новую версию. Ошибка оставляет решение неиспользованным и стадию прежней. Решение владельца не является независимой проверкой достоверности внешних данных или ревизии; текущие записи reviewer и экономика требуют отдельной настоящей проверки.

Никаких запросов в Telegram или Ozon этот модуль не делает. Будущий шлюз для внешней записи должен независимо проверить лимиты, права, актуальность решения и записать намерение в журнал в **той же транзакции и на том же соединении**, что и `consume_in_transaction`; неопределённый результат внешнего запроса нельзя повторять автоматически. Переход стадии не разрешает публикацию или вызов Ozon.

Серверная команда для подготовки запроса (без отправки в Telegram): `python3 -m gates.request --db /путь/к/базе.sqlite3 --gateway-db /абсолютный/путь/к/gateway.sqlite3 --candidate-id ID --revision N --gate sample`. Telegram ID владельца и чата должны быть настроены в переменных `TELEGRAM_OWNER_USER_ID`, `TELEGRAM_OWNER_CHAT_ID` процесса сервера. Результат содержит nonce и полный пакет: его следует передать только доверенному процессу бота. Цикл запущенного серверного бота автоматически формирует готовые запросы, отправляет ожидающие решения и по подтверждению выполняет локальный переход; в текущем окружении бот и таймер не установлены и не запущены. Маршрута создания запроса через Gateway нет: команду выполняет только доверенный администратор на сервере.

## Автоматическое создание заявок

Доверенный серверный процесс может вызвать `gates.worker.scan(store)` или `python3 -m gates.worker --db /путь/к/базе.sqlite3 --gateway-db /абсолютный/путь/к/gateway.sqlite3` (нужны настроенные `TELEGRAM_OWNER_USER_ID` и `TELEGRAM_OWNER_CHAT_ID`). Worker за один проход проверяет не более 20 товаров и автоматически создаёт запрос на текущих воротах: для запуска и публикации сначала отдельный запрос прав, затем — само решение. Отказанные и истёкшие запросы не создаются повторно; они требуют ручного разбора. Если одобрение записано, но переход прервался, повторный проход пытается восстановить его идемпотентно. Вывод — только счётчики и фиксированные коды блокировок. Worker не отправляет сообщения и не вызывает Ozon. Цикл бота сначала обрабатывает /stop, затем проверяет остановку шлюза и только при отсутствии остановки запускает worker и отправку запросов. GateStore и worker берут ту же блокировку, что и stop, затем повторно проверяют состояние шлюза. Блокировка удерживается отдельно на каждого кандидата: переход либо завершится до зафиксированной остановки, либо будет ею заблокирован; сетевых обращений под блокировкой нет. После партии из 20 товаров бот возвращается к получению обновлений Telegram. Сохранённый курсор по первому ID кандидата продолжает обход со следующего товара, а по окончании списка возвращается в начало; это предотвращает голодание поздних записей даже после перезапуска. Это действует только если все процессы используют тот же абсолютный путь к защищённой базе шлюза и этот программный контур; прямое изменение файлов или другая база обходят его. Сам шлюз также независимо блокирует внешние записи. Standalone CLI требуют путь к существующей базе шлюза и выполняют ту же синхронизированную проверку stop; при недоступном шлюзе они не вносят изменений. Неполные данные, изменившаяся версия или отсутствие обязательных полей блокируют заявку.

При встраивании используйте `GateStore(path, owner_user_id, owner_chat_id, gateway=GatewayStore(absolute_gateway_db))`. Без шлюза изменяющие методы fail-closed. `with store.coordinated():` допускает вложенные вызовы на одном объекте и потоке; держать её во время сетевых вызовов запрещено. Для будущего шлюза необходимо согласовать порядок блокировок до выполнения записей в Ozon.
